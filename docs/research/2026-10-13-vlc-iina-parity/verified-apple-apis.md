# Verified AppKit/SwiftUI claims (2026-10-13)

Primary sources fetched directly (raw GitHub, Apple DocC JSON). IINA = iina/iina `develop`; mpv = `master`; VLC = `master`.

## 1. performDrag(with:) in mouseDown / clickCount
Verdict: "blocks until mouseUp" is WRONG. "Breaks clickCount==2" is UNSETTLED (no evidence either way).
- Apple doc: "This method returns right away, and a mouse-up event may not get sent." Also: "Your application (or a view) can call this method after receiving and examining a mouse-down event ... hand off the work to the Window Server process." https://developer.apple.com/documentation/appkit/nswindow/performdrag(with:)
- So the real hazard is the opposite one: after performDrag the view may never get mouseUp (so any "pressed" state must be cleared by you).
- Apple's Photo Editor sample calls it only after a drag threshold, from inside a `trackEvents` loop (that loop is what blocks, not performDrag): "trackEvents won't return until after the tracking all ends" ... `if (fabs(currentPoint.x - startingPoint.x) >= 5 ...) { stop.pointee = true; window.performDrag(with: event) }`, and on `.leftMouseUp` it reposts the event. https://developer.apple.com/library/archive/samplecode/PhotoEditor/Listings/Photo_Editor_WindowDraggableButton_swift.html
- Threshold-in-mouseDragged pattern: CONFIRMED for IINA. `MainWindowController.mouseDragged`: `if mousePosRelatedToWindow.distance(to: event.locationInWindow) <= minimumInitialDragDistance { return }; isDragging = true ...; window?.performDrag(with: event)`. Note IINA passes the mouseDragged event, not the original mouseDown (differs from your claim "with the original mouseDown event"). Its comment: "The user's action will only be counted as a click if `isDragging==false` when `mouseUp` is called." IINA double-click handling is in mouseUp: `if event.clickCount == 2 && event.inAnyOf([titleBarView])`. https://github.com/iina/iina/blob/develop/iina/MainWindowController.swift
- mpv: CONFIRMED threshold pattern, and it uses the original mouseDown event. input.c: "Begin built-in VO dragging if the mouse moves while the dragging button is down ... `ictx->last_doubleclick_time = 0;` // Prevent activation of MBTN_LEFT_DBL if VO dragging begins." then queues `begin-vo-dragging`; `video/out/mac/window.swift startDragging()` does `guard let event = view.lastMouseDownEvent ... performDrag(with: event)`; view.swift mouseDown stores `lastMouseDownEvent = event` and `hasMouseDown = event.clickCount <= 1`. https://github.com/mpv-player/mpv/blob/master/input/input.c , https://github.com/mpv-player/mpv/blob/master/video/out/mac/window.swift
- Net: both apps defer drag until movement past a deadzone; mpv explicitly suppresses double-click after a drag begins, which implies double-click and drag interact. performDrag from the first mouseDown with no threshold would take every click away from you (my inference).

## 2. contentAspectRatio vs programmatic setFrame
Verdict: CONFIRMED (docs), with a caveat about live AppKit behavior.
- Apple doc: "the dimensions of its content rectangle are constrained to integral multiples of that ratio when users resize it. You can set a window's content view to any size programmatically, regardless of its aspect ratio." https://developer.apple.com/documentation/appkit/nswindow/contentaspectratio
- mpv does not rely on it for programmatic sizes: `override func setFrame(...) { ...; super.setFrame(frameRect, display: flag); if keepAspect { contentAspectRatio = unfsContentFrame.size } }` (re-asserts the ratio after every programmatic frame change). https://github.com/mpv-player/mpv/blob/master/video/out/mac/window.swift
- Not found: any forum/code evidence that setFrame is ever silently corrected to the ratio. Compute the correct frame yourself.

## 3. SwiftUI .commands vs manual NSMenuItems; @FocusedObject
Verdict: UNSETTLED for "SwiftUI removes/rebuilds manual items" (no primary evidence found); @FocusedObject reliability: UNSETTLED/leaning "flaky".
- Fetched Apple forum 649096, 695325 and steipete's post: none states SwiftUI rebuilds `NSApp.mainMenu`. Evidence is indirect: steipete: "we have to skip a runloop so the SwiftUI glue has time to set up the menu" (SwiftUI populates the menu after launch; he mutates NSApp.mainMenu from DispatchQueue.main.async on appear and on state change, implying it must be re-applied). https://steipete.me/posts/2021/top-level-menu-visibility-in-swiftui
- A web-search summary claimed "SwiftUI will restore the menus"; I could not locate that sentence on the pages fetched, so do not rely on it.
- Focus values: Apple forum thread 693580 reports menu becoming disabled after switching apps and back with focusedSceneValue, filed as SwiftUI bug, and that it seemed to work with WindowGroup but not single Window. https://developer.apple.com/forums/thread/693580 . Other threads (651748, 681973) report @FocusedBinding/@FocusedValue of class-typed models not refreshing menus. troz.net (2025) says `focusedSceneObject` worked for ObservableObject but not cleanly with Observation. https://troz.net/post/2025/mac_menu_data/ . Not tested on macOS 26.
- Recommendation: treat as needing a runtime test on macOS 26; keep a fallback (e.g. route via NotificationCenter/key window lookup).

## 4. Bare-key SwiftUI menu Button vs focused text field
Verdict: UNSETTLED (sources conflict; nothing SwiftUI-specific).
- Apple doc order: "The application object handles key equivalents by going down the view hierarchy in the key window, sending each object a performKeyEquivalent: message until an object returns YES. If the message isn't handled ... NSApp then sends it to the menus in the menu bar." keyDown to first responder comes after. https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/EventArchitecture/EventArchitecture.html
- Evidence menus DO steal: JUCE report, NSMenu command with right arrow and no modifiers "stops the right arrow key working when a TextEditor has focus"; JUCE added "Mac MainMenu: Allow commands without modifiers to be passed to peer." https://forum.juce.com/t/br-some-macos-menu-shortcuts-steal-keypresses-to-texteditor/46813 (arrow = function-key flag, not a letter).
- Evidence they may NOT: old Cocoa-dev threads (2008-2009) reportedly observed bare space going to the text field first, only arrows/command-flagged events going to the menu first. I could not re-fetch them (502); treat as unverified recall. https://lists.apple.com/archives/Cocoa-dev/2009/Dec/msg01295.html
- No SwiftUI forum thread or Feedback ID found for `.keyboardShortcut("m", modifiers: [])` + TextField. Test empirically; safer to gate the command with `.disabled(isTextFieldFocused)` or avoid bare letter shortcuts in menu items.

## 5. addLocalMonitorForEvents(.keyDown) returning nil vs main menu
Verdict: CONFIRMED in effect (monitor runs first), but only indirectly sourced.
- Apple Monitoring Events guide: local monitors get events "prior to their dispatch"; returning nil drops the event (Apple's sample returns nil for Escape/Enter). https://developer.apple.com/library/mac/documentation/cocoa/conceptual/eventoverview/MonitoringEvents/MonitoringEvents.html
- Ghostty uses exactly this ordering knowledge: its local monitor calls `mainMenu.performKeyEquivalent` itself so that menu shortcuts keep priority over its own handling (implying the monitor would otherwise pre-empt them). https://github.com/ghostty-org/ghostty (AppDelegate key monitor)
- FreePascal bug 35449 reportedly lists the same order; I could not fetch it (DNS), unverified.
- So returning nil for a key stops the menu equivalent; to defer to menus call `NSApp.mainMenu?.performKeyEquivalent(with:)` first.

## 6. deltaY vs scrollingDeltaY; VLC scrollWheel
Verdict: PARTLY CONFIRMED. The "~/10" ratio is an empirical convention, not documented.
- Apple: scrollingDeltaY "is the preferred property for accessing delta values. When hasPreciseScrollingDeltas is true, multiply by line or row height. Otherwise scroll by the returned amount." deltaY doc: "For scroll wheel events, use scrollingDeltaY instead." https://developer.apple.com/documentation/appkit/nsevent/scrollingdeltay
- GLFW (cocoa_window.m): `if ([event hasPreciseScrollingDeltas]) { deltaX *= 0.1; deltaY *= 0.1; }`. SDL (SDL_cocoamouse.m): `x = -[event scrollingDeltaX] * 0.1f; y = [event scrollingDeltaY] * 0.1f;` for precise, else uses `deltaX/deltaY`. So deltaY ~ lines, precise scrollingDeltaY ~ 10x per line is the de facto convention.
- VLC `VLCVoutView.m scrollWheel:` uses `deltaY`, not scrollingDeltaY: `CGFloat f_deltaY = [theEvent deltaY]; if ([theEvent isDirectionInvertedFromDevice]) { f_deltaX = -f_deltaX; f_deltaY = -f_deltaY; }`; mouse wheels (`subtype == NSEventSubtypeMouseEvent`) with |dy| < 1.0 are bumped to ±1.0 (`f_yThreshold = 1.0`, `f_directionThreshold = 0.05`); then `f_cumulatedYScrollValue += f_deltaY; while (ABS(f_cumulatedYScrollValue) >= f_yThreshold) { ... var_SetInteger(..., "key-pressed", key) }`; axis lock: after one axis fires the other is ignored until a 0.4 s NSTimer resets (`resetScrollWheelDirection`). https://github.com/videolan/vlc/blob/master/modules/gui/macosx/windows/video/VLCVoutView.m
- Momentum: VLC does NOT filter. No `phase`/`momentumPhase` check in that method (grep found none), so momentum events are included and accumulate. IINA filters: `if !isMomentumScrollingAllowed && !event.momentumPhase.isEmpty { return }` and for non-precise wheels uses `scrollingDeltaY.unifiedDouble * 2` (sign only), precise uses `scrollingDeltaY` raw. https://github.com/iina/iina/blob/develop/iina/MainWindowController.swift , PlayerWindowController.swift

## 7. MPRemoteCommandCenter / MPNowPlayingInfoCenter, non-AVPlayer
Verdict: CONFIRMED that playbackState must be set explicitly on macOS. Entitlements: UNSETTLED (none known required).
- Apple: "This property only applies to macOS. You must set this property every time the app begins or halts playback, otherwise remote control functionality may not work as expected." https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter/playbackstate
- IINA NowPlayingInfoManager: `center.playbackState = paused ? .paused : .playing` (and a workaround: "setting playbackState initially to playing and then immediately set it to paused" because "Now Playing [may] drop IINA and go back to showing the Music app"). On teardown `center.playbackState = .stopped`. https://github.com/iina/iina/blob/develop/iina/NowPlayingInfoManager.swift . IINA RemoteCommandController: `MPRemoteCommandCenter.shared()`, `playCommand.addTarget { ... return .success }`, with the note "it is critical that IINA releases control when no media is open" (issue #4331). (AppDelegate.swift doc comment.)
- mpv osdep/mac/remote_command_center.swift: `infoCenter.nowPlayingInfo = nil; infoCenter.playbackState = .unknown` on disable; `makeCurrent(){ playbackState = .paused; playbackState = .playing; ...}`; `playbackState = isPaused ? .paused : .playing`; media type video. https://github.com/mpv-player/mpv/blob/master/osdep/mac/remote_command_center.swift
- Neither is AVPlayer-based; both are CoreAudio/own-engine. Entitlements: IINA/mpv are not sandboxed; I found only one Apple forum report (thread 678108) of an ignored `playbackState` call for a missing "mediaremote set-playback-state" entitlement, context unclear (not verified for macOS app targets). Test under your sandbox config. Also add `isEnabled = true` on commands.

## 8. NSURLFileResourceIdentifierKey persistence
Verdict: WRONG to assume persistent. Apple: "Two resources are equal if they have the same file-system path or if their paths link to the same inode on the same file system. The value of this identifier isn't persistent across system restarts." https://developer.apple.com/documentation/foundation/urlresourcekey/fileresourceidentifierkey
- Related: `fileIdentifierKey` doc says "isn't stable for all file systems or across all mounts ... don't persist it" (even though an Apple engineer on forums says HFS/APFS inode IDs survive reboot/rename). Use bookmarks for storage; use `fileIdentifier` only for in-session equality.

## 9. SwiftUI overlay above NSViewRepresentable with CAMetalLayer
Verdict: UNSETTLED. No primary report found either way.
- Nothing in Apple docs/forums fetched states SwiftUI siblings are drawn beneath a CAMetalLayer-backed NSViewRepresentable. In SwiftUI `ZStack`/`.overlay`, later siblings are composited above the hosted NSView (the representable is just another view in the hosting hierarchy); known issues center on sheets/MTKView (e.g. forum thread 764470 "Cannot Display MTKView on a sheeted view on macOS15"), not overlay order. mpv-in-SwiftUI via `wid` with a separate window-level surface is a different risk (wid takes over the layer), and the repo's own CLAUDE.md notes layer setup order. Verify visually on macOS 26; keep overlays as SwiftUI siblings after the representable (not AppKit-layer zPosition tweaks).

## 10. window.level = .floating with native fullscreen
Verdict: CONFIRMED as a known-problem area; IINA's approach quoted.
- IINA never applies floating while native fullscreen: `override func setWindowFloatingOnTop(_ onTop: Bool, ...) { guard !fsState.isFullscreen else { return }; super...` ; on entering native FS it calls `setWindowFloatingOnTop(false, updateOnTopStatus: false)` and on exit/playing it restores `if player.info.state == .playing { setWindowFloatingOnTop(isOntop, updateOnTopStatus: false) }`. Base: `window.level = onTop ? .iinaFloating : .normal` where `iinaFloating = NSWindow.Level(NSWindow.Level.floating.rawValue - 1)`. The IINA "legacy fullscreen" path instead sets `window.level = .floating` (and `housingWindow.level = .mainMenu` for notch hiding) because it is a borderless non-Space window. https://github.com/iina/iina/blob/develop/iina/MainWindowController.swift , PlayerWindowController.swift:663 , Extensions.swift
- mpv `setOnTop` sets `.floating` / `.statusBar + 1` etc. on the mpv window (its own fullscreen is custom animation, not Space-based). https://github.com/mpv-player/mpv/blob/master/video/out/mac/window.swift
- Apple forums: floating level does not put a regular window above another app's full-screen Space; DTS suggests accessory activation policy + nonactivating NSPanel + `.fullScreenAuxiliary`/`.canJoinAllSpaces` (https://origin-devforums.apple.com/forums/thread/826308 , https://developer.apple.com/forums/thread/738308). That concerns overlay-above-other-apps, not your own FS Space, but it supports "don't bother with level in native FS".
