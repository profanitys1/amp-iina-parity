## A. Verified bug list (CONFIRMED in code)

**A1. FloatingOSC scrubber sends an unthrottled exact seek on every drag event.**
- `UI/FloatingOSCView.swift:108` passes `onScrub: { controller.seekTo($0) }`. `UI/PlayerScrubber.swift:60-68` calls it from `DragGesture.onChanged` and `.onEnded`. `PlayerController.seekTo` (`Logic/PlayerController.swift:1251`) cancels throttling and calls `MPVPlayer.seek(to:)`, which issues `seek <t> absolute` (`MPVPlayer.swift:529-537`), i.e. mpv's precise seek, once per mouse event. `ControlsView.swift:626/639` and `AudioWaveformView.swift:218/222` already use `scrub(to:)` (throttled `absolute+keyframes`, `MPVPlayer.swift:542-551`) then `endScrubbing(at:)`.
- FloatingOSC is the control for all non-Compare playback (`ContentView.swift:455-465`; `ControlsView` only when `compareSession.isActive || isLoading`).
- Impact: laggy drag on long-GOP content; decoder thrash. The review's "10x smoother" is unmeasured.
- Minimal fix: add `onEndScrub` to `PlayerScrubber`; in `FloatingOSCView` use `onScrub: controller.scrub(to:)`, `onEndScrub: controller.endScrubbing(at:)`; keep the VoiceOver adjustable action on `seekTo`.

**A2. `addSubtitle` never refreshes the track list.**
- `Logic/PlayerController.swift:1533-1535` just calls `mpvPlayer?.addSubtitle` (`sub-add <path> select`, `MPVPlayer.swift:1578`). `track-list` is not observed, and the only MPV option rebuild helper, `buildMPVSubtitleTrackOptions()` (`PlayerController.swift:1518`), has zero callers (dead). Callers of `addSubtitle`: `ContentView.swift:119`, `ContentViewCommandHandlers.swift:188`, `PlayerWindowCoordinator.swift:249`.
- Impact: a subtitle added from the menu or drag-drop is selected in mpv but absent from the Subtitles menu.
- Minimal fix: after `addSubtitle`, call `refreshAudioTrackOptions(playerItem: nil)` (same call used at `PlayerController.swift:616`); delete `buildMPVSubtitleTrackOptions`. `sub-add` is a synchronous command, so the list is current on return. Verify manually (add `.srt`, open menu).

**A3. `.efficient` silently loses its neural doubler on every 120 Hz Mac, while the picker still prices it as if present.**
- `MPVPlayer.swift:1390` strips any path containing `FSRCNNX` when `displayRefreshRate > 60`. `displayRefreshRate` is `screen.maximumFramesPerSecond` (`MPVVideoView.swift:364`), so 120 on every ProMotion MacBook regardless of source fps. Added in commit `4316b70` (after interpolation shipped in `fbebae6`), with no measurement.
- `.efficient` = `[FSRCNNX_x2_8-0-4-1, KrigBilateral]` (`RenderProfile.swift`), priced at 10.9/18.5 ms (`ProfilePicker.swift` costs) and used as `.compressed`'s first fallback (`ProfilePicker.chain`). On the owner's machine the fallback runs Krig alone (no upscaler), the badge still says "Efficient upscale", and GPU monitoring sees a much cheaper stack than the cost table predicted.
- The review's guess that the filter exists only because interpolation was forced is roughly right in effect (the rule is keyed to panel max, not source rate) but not documented in the code.
- Minimal fix: gate on the real condition, not the panel max: strip FSRCNNX only if interpolation is active AND measured budget fails, or simply remove the filter and let `GPUBudgetMonitor` step down. Record the decision in a comment.

**A4. `syncTimecode` aligns windows to the 100 ms-coalesced UI time.**
- `UI/ContentViewCommandHandlers.swift:503`: `let relTime = controller.currentPlaybackTime`. `MPVPlayer.timePosPublishInterval = 0.1` (`MPVPlayer.swift:74`). `PlayerController.playbackTimeSnapshot()` (`PlayerController.swift:1334`) exists for exactly "frame-sensitive review actions".
- Impact: Align-to-timecode can be up to ~100 ms (2-6 frames) off while playing; exact when paused.
- Fix: one-word change to `controller.playbackTimeSnapshot()`. Review's other claim in D8 (play/pause mismatch after align) is a behaviour choice, not a bug.

**A5. Loop ignores trim range.** `MPVPlayer.setLooping` (`MPVPlayer.swift:512-516`) sets only `loop-file=inf|no`; no `ab-loop-a/b` anywhere in the code. CONFIRMED as a gap; it is a product decision (F1.1), not a defect. Listed in B-section.

**A6. Dead code (CONFIRMED, trivial):** `PlayerController.buildMPVSubtitleTrackOptions` (`PlayerController.swift:1518`), `MPVPlayer.commandString` (`MPVPlayer.swift:1583`). Four near-identical waveform generation blocks exist: `ContentView.swift:658`, `ContentViewCommandHandlers.swift:305`, `AudioWaveformView.swift:256`, `AudioWaveformWindowController.swift:156`. Real, but pure cleanup.

**A7. Stale comment, not a bug:** `MPVPlayer.swift:347-351` says `hwdec-extra-frames=4` sizes the hwdec pool for interpolation. mpv's manual says that option only applies to APIs that preallocate surfaces (d3d11va, vaapi); videotoolbox allocates on demand. Already flagged in `docs/research/2026-10-03-engine-improvements.md` section 1; still unfixed. Fix the comment or drop the line.

## B. Verified improvements worth doing

Ordered by value per effort. "Evidence" cites what I checked.

**B1. Stop the reload-on-resize/fullscreen hack by fixing the cause in the fork's moltenvk context. Effort M. Risk medium. Highest value.**
- Facts: AMP posts `.reloadPlayer` (destroying mpv) on first >=1.5x drawable growth (`MPVVideoView.swift:234-246`), on `didEnterFullScreen` (:313-315), `didExitFullScreen` (:333-335), `didEndLiveResize` (:351-353); `requestReloadForSurfaceChange` posts at :393-394. The in-code comment (:368-387) records that "lighter nudges" (seek, `video-zoom=0`) did not work.
- Root cause found (the review's mechanism is wrong, its direction is right): in mpv master `vo_gpu_next.c`, the destination rect is recomputed only in `resize(vo)` (:1828), which runs from `reconfig` or when a context `control()` returns `VO_EVENT_RESIZE` (:2242). Upstream `macvk` returns that event (`context_mac.m:141`). The MPVKit `moltenvk` context never does (`control` returns `VO_NOTIMPL`; 0004 only handles `VOCTRL_VO_OPTS_CHANGED`). `ra_vk_ctx_resize` (which sets `vo->dwidth/dheight`, `vulkan/context.c:526`) is only called from `moltenvk_reconfig`. So libplacebo's swapchain follows `drawableSize`, but `vo->dwidth` and the dst rect stay at the old size: exactly the "top-left quadrant" symptom, present both paused and playing.
- Two fixes:
  1. Proper (fork patch, `0001`/`0004`): in `moltenvk_control`, remember the last `layer.drawableSize`; on `VOCTRL_CHECK_EVENTS` (or any control call; verify which request the VO thread issues for this vo) compare, call `ra_vk_ctx_resize(ctx, w, h)` and set `*events |= VO_EVENT_RESIZE`. About 15 lines of C. Needs MPVKit rebuild + re-pin (`Package.resolved`).
  2. Zero-rebuild probe: `player/command.c:8483-8486` sends `VOCTRL_EXTERNAL_RESIZE` when `android-surface-size` or `d3d11-composition-size` changes at runtime. vo_gpu_next handles it as `reconfig(vo, NULL)` -> `moltenvk_reconfig` (reads `layer.drawableSize`) -> `resize(vo)`. Setting `android-surface-size` to a different `WxH` string each time after the layer settles should refresh the dst rect without recreating mpv. Both options are plain `OPT_SIZE_BOX` (`options.c:253,256`), not fixed. This is a hack on unrelated option names; unverified on this build (needs one on-device test).
- The review's `CATransaction.setDisableActions` suggestion is harmless and cheap but unproven as the cause (see C3). Do not count on it.
- Verify: with fix 2 or 1 in place, remove the three notification-triggered reloads and the growth rule; test: open a small clip, enter/exit fullscreen paused and playing, live-resize drag, drop a file into a small window; picture must fill the layer each time. Check `scaling` OSLog category.
- Risk: removing the reloads without confirming the fix regresses the exact bug they fix. Keep the reload as a fallback guarded by an app setting until validated.

**B3. Cost model: gate neural prescalers on real upscaling and stop scaling source-only cost by the window. Effort S-M. Risk low.** (review E1/H#13; also in-repo doc 2026-10-03 "Gap 4". CONFIRMED.)
- Facts: `ProfilePicker.estimatedMilliseconds` returns `base * drawablePixels / referenceDrawablePixels` (`ProfilePicker.swift:71`), so cost scales with source x window. ArtCNN and FSRCNNX hooks are source-sized and self-gate: actual `//!WHEN OUTPUT.w LUMA.w / 1.3 > OUTPUT.h LUMA.h / 1.3 > *` (the review quotes `NATIVE.w / 1.200`; real threshold is 1.3 against `LUMA`, verified in `~/.config/mpv/shaders/ArtCNN_C4F16.glsl:31` and `FSRCNNX_x2_8-0-4-1.glsl:17`). When the window is not >=1.3x the source in both axes, libplacebo skips them for free, yet the picker prices them as expensive and, for a 4K clean file in a window smaller than 4K, falls past them to `.sharpen` (`SSimSuperRes` + `ewa_lanczossharp`, `scaler-resizes-only=no`) on a source that is being downscaled. `SSimSuperRes` itself self-gates on `NATIVE_CROPPED < OUTPUT`, so it is also a no-op when downscaling; the visible side effect is just the `scale` change to `ewa_lanczossharp` for downscales (only `scale`, and `dscale` governs downscaling, so likely harmless). Real cost of the mis-pricing: wrong profile labels/budget rejections and wasted analysis, not visible damage.

- Risk: `.compressed` bundles hdeband/nlmeans/CfL which still help when not upscaling. Do not drop it blindly for compressed sources; apply the gate only to the neural stages, e.g. by adding a non-upscaling variant, or keep `.compressed` and accept the free skip. **B4. Budget monitor should respect when interpolation is actually pointless. Effort S. Risk low-medium.** (review C3/H#9 reframed.)

Everything else unchanged (25, 24.917, 29.97 on 120 stays interpolated).
- Evidence: 24 and 30 and 60 fps on 120 Hz are exact; 23.976 is within the 1% that `display-resample` absorbs.

Real mechanism: 20+ views hold `@ObservedObject var controller: PlayerController` (e.g. `FloatingOSCView.swift:19`, `PlayerView.swift:12`, `ContentViewCommandHandlers.swift:14/74/350/481`) and `currentPlaybackTime` is `@Published` updated at 10 Hz (`PlayerController.swift:68`, `timePosPublishInterval` 0.1). Each tick fires `objectWillChange` for all of them. The "~70% less main-thread CPU" figure is invented. Do a SwiftUI Instruments trace on a 4K playback first; a cheaper step is moving the time into a small separate `ObservableObject` read only by scrubber/timecode views. Effort L, risk medium.
- Reusing one `MPVPlayer` across files (D4.3/H#29): plausible win, "250 ms -> 15 ms" is unmeasured, and AMP creates mpv with options that are hard to change after init (`wid`, `vo`, `hwdec` choice tied to `correctsReflection`, `screen-name`). Also entangled with B1. Defer until B1 lands; measure open-next-file latency first.
- Diagnostics: a "Copy Diagnostics" command (macOS, chip, mpv/libplacebo versions, `hwdec-current`, `vo-passes`, active profile, last log lines) is cheap (S) and valuable for the MPVKit fork; `mpv_request_log_messages` is already at `error` level in release builds (`MPVPlayer.swift:~322`), so a 50-line ring buffer is easy.
